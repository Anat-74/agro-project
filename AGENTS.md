## Новая сессия — обязательно сообщить пользователю

Если сессия началась заново (после перезапуска/компактации), **первым же сообщением** прямо указать:
«Началась новая сессия — прежний контекст недоступен; опираюсь на файлы: …» и перечислить,
что прочитано (AGENTS.md, patterns.md §7–§9, cards-notch.md и т.д.). Не продолжать работу молча,
делая вид, что помнишь историю.

## CRITICAL: git push / deploy запрещены без явной команды

- **"закомить"** — только `git commit`, без push.
- **"запуш" / "запушкать"** — ЕДИНСТВЕННАЯ команда для `git push`.
- **"деплой" / "задеплой"** — ЕДИНСТВЕННАЯ команда для запуска `node scripts/deploy.mjs`.
- **"деплой изменения" / "задеплой изменения"** — полная цепочка: `git add` (только нужные файлы) → `git commit` → `git push` → `node scripts/deploy.mjs`. Логика: деплой тянет код из удалённого git, поэтому незапушенные изменения до прода не доедут. Подтверждения пуша в этом случае не требуется.
- Если пользователь сказал что-то другое (например "закомить", "делай", "продолжай", "ок") — НЕ пушить и не деплоить.
- Нарушение этого правила — критическая ошибка агента.

## Поиск актуальной информации в интернете — обязательный инструмент

У агента есть веб-поиск (`deepseek-search`), MCP-доки Nuxt/Vue и официальная документация Strapi.
Пользоваться ими нужно, а не полагаться на память — это экономит время и деньги.

- **Перед обновлением зависимостей/модулей** — сначала найти release notes и breaking changes
  (GitHub Releases, docs), потом ставить.
- **Если что-то не получается, поведение необъяснимо или есть сомнение** в синтаксисе/API —
  **сначала поиск** (официальные доки → GitHub issues → Stack Overflow), потом правки.
  Две неудачные попытки «по памяти» → идти в интернет.
- Для Nuxt/Vue в первую очередь MCP-доки (`nuxt-docs`, `vue-docs`), для Strapi —
  `docs.strapi.io` (можно читать `llms-full.txt`).
- Если решение основано на внешнем источнике — указать ссылку в отчёте.
- Не выдавать догадку за факт: «проверено» только то, что реально проверено (тест/сборка/поиск).

## Компоненты — с оглядкой на Vue Vapor Mode

**Пиши компоненты Nuxt 4 с учетом Vapor Mode (без использования VDOM-зависимых API).**

- Шаблоны + `<script setup>` + reactivity (`ref`, `computed`, `watch`) — основа.
- Не использовать: `h()` и render-функции, ручное создание/обход VNode,
  `getCurrentInstance().vnode`, `$forceUpdate`, VDOM-хуки (`onVnodeMounted` и т.п.),
  плагины/директивы, завязанные на VNode.
- Слоты, `v-if/v-for/v-model`, `defineModel`, `useTemplateRef` — допустимы.
- Если без VDOM-API не обойтись — писать об этом в отчёте и предлагать альтернативу.

## Проверка сайта после деплоя — НЕ нужно

- **Сайт после деплоя проверяет сам пользователь** — агент НЕ должен открывать прод, браузером ходить по сайту или долго «проверять работу после билда».
- После запуска `node scripts/deploy.mjs` достаточно отчёта: коммит, пуш, «Build запущен (3–5 мин)» — и остановиться.
- Исключение: только если пользователь явно попросил проверить.

## Перезапуск приложений — делает пользователь сам

- **Перезапуск фронта/API после деплоя пользователь выполняет сам.** Не предлагать это и не спрашивать «перезапустить?» — агент только сообщает, что для появления сборки на проде нужен перезапуск (без вопроса).
- Запускать `scripts/restart-app.mjs` / `scripts/restart-api.mjs` самостоятельно — только по прямой команде пользователя («перезапусти»).

## Remote work — формат ответа

- При удалённой работе (через Telegram-бота) отвечать **в формате .md**: заголовки, списки, блоки кода, таблицы — чтобы ответ был читаем в Telegram.
- Исключение: односложные ответы ("да", "нет", "готово") — без .md.

## File editing

- On Windows, use the `edit` tool for all file modifications. Do NOT use `bash`/`shell`/`cat`/heredocs for editing files — the Windows shell (PowerShell/MINGW64) does not reliably support heredoc syntax and complex command-line escaping.
- The project has `edit` tool available. Always check your tool list before falling back to shell commands.
- Use `read` to review file content, then `edit` to apply changes. Use `bash` only for running commands (git, npm, build), not for file manipulation.

## Пиковые и не пиковые часы (стоимость токенов)

Время по UTC+3 (Московское). Не пиковые часы — стоимость токенов в 2 раза ниже.

- **НЕ пиковые (дешевле ×2):** с 7:00 до 9:00 и с 13:00 до 4:00 следующего дня.
- **Пиковые (дорого):** с 9:00 до 13:00 и с 4:00 до 7:00.

Правила работы:
- **Объёмные работы** (большой анализ кода, проверки на проде, длинные операции, генерация больших объёмов) — выполнять в **не пиковые часы**.
- **В пиковые часы** — только лёгкая работа с минимальным расходом токенов: мелкие правки, короткие ответы, без больших анализов и проверок.
- Если агент видит, что задача **в пиковое время** потребует большого расхода токенов — он **обязан предупредить пользователя** и предложить перенести на не пиковые часы либо выполнить минимально.

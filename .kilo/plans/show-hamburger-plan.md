## Недочёты/баги, которые чиним

1. **Дубликат id** `hamburgerDialog`/`dialogHamburger` (AppHeader рендерит два инстанса) → в `useDialogState.ts` последний зарегистрированный элемент перезаписывает первый → на desktop кнопка открывает скрытый мобильный диалог, desktop-диалог не получает `[open]`.
2. **Tablet (768–1024):** телепорт активен + dropdown-стили `@media (min-width: $mobile)` → `top: calc(100% + 22px)` от `body` = окно за вьюпортом (822px).
3. **a11y:** `.dialog-hamburger { display: grid }` перебивает UA `dialog:not([open]){display:none}` → закрытый диалог остаётся в дереве доступности.
4. **Рассинхрон границ:** CSS `$tablet` 1023.98 vs JS `isTablet <= 1024` (после перехода на `$mobile` — выровнять).
5. **`useViewport` не SSR-safe** (`width = 0` на сервере) — мешает «open by default».

## Шаги реализации

### Шаг 1. Разделение id и состояний инстансов
- Уникальные id диалогов через проп: `dialog-hamburger-desktop` / `dialog-hamburger-mobile`.
- Отдельные ключи состояния `useDialog`: `hamburgerCatalogDesktop` (desktop-панель) и `hamburgerDialog` (mobile-оверлей, как сейчас).
- `HeroGrids`/`USocials` (grayscale) остаются на `hamburgerDialog` (mobile).

### Шаг 2. `useDialogState.ts` — локальный ref
- `open()`/`close()` работают с **локальным** `dialogElement` (переданным в вызов), а не с глобальным `dialogElementMap` (map оставляем только для id-only читателей `isOpen`).
- Тест `useDialog.spec.ts` — дополнить случаем «два элемента, один id».

> ✅ **Реализовано 08.26:** шаг 1 и 2 — проп `dialog-id` (desktop/mobile), ключи разведены, `open/close` на локальном ref (`dialogElementMap`/`optionsMap` удалены). Проверено: desktop-кнопка открывает СВОЮ панель (раньше — скрытый mobile-диалог).

### Шаг 3. Breakpoint > `$mobile`
- Dropdown-ветка диалога (`@media (min-width: $mobile)`, 320→235, под кнопкой) — **уже соответствует** новому разбиению: применяется на всех экранах >768 (включая прежний tablet-диапазон 768–1024 — теперь это desktop-режим, без телепорта).
- Full-screen оверлей — базовые стили (≤768); телепорт в `<body>` — **только** `isMobile = width <= 768`.
- `useViewport`/детект: заменить `isTablet (<=1024)` на `isMobile (<=768)`; выровнять границу JS/CSS.

### Шаг 4. Anchor Positioning
```scss

  position-anchor: --hamburger-menu;
  position-area: bottom span-right;
```

## Вложенные подкатегории в details (решение 08.27)

**Текущее:** подкатегория — обычная ссылка (сразу переход на страницу подкатегории).
**Нужно:** подкатегория — вложенный `<details>` внутри категории (клик раскрывает её товары, НЕ переходит); переход — только по товару (как у прямых товаров категории); у названия подкатегории — шеврон `mingcute:down-line`.

Структура:
```
Категория (details + шеврон)
  └─ Подкатегория (details + шеврон)
  │    └─ Товары подкатегории (ссылки → страница товара)
  └─ Товары категории (как сейчас)
```

Технические моменты:
1. **Данные:** в fetch категорий добавить populate `subcategories.products` (сейчас только `name, slug, image`). Товарам — `fields: name/slug` + `image` + `category` + `subcategory` (для `getProductLink`).
2. **`name="faq"` конфликт:** у вложенных подкатегорий НЕ ставить общий `name="faq"` (иначе открытие подкатегории закроет родительскую категорию — нативная эксклюзивная группа). Своя группа: `name="faq-${cat.slug}"` (подкатегории эксклюзивны внутри своей категории).
3. **Активные ссылки:** у подкатегории подсветка — на её summary (маршрут `/${locale}/${cat.slug}/${sub.slug}`), у товаров — как обычно по `getProductLink`.
4. **Шрифт подкатегории:** на 1px больше, чем у товаров (у товаров `toEm(16)`? — уточнить текущий размер; подкатегория +1px).
5. **Эффект «вдавливание» вокруг подкатегории с картинкой** — паттерн USelect (`USelect.vue:101-112`):
   ```scss
   border: toRem(1) solid var(--border-color);

     inset 0 toRem(2) toRem(3) rgba(0, 0, 0, 0.25),   // вдавленность (внутр. тень сверху)
   ```

## Anchor Positioning для desktop-панели (анализ 09.09, отложено)

**Решение (Шаг 4 плана):** нативный Anchor Positioning (`style-guide` §14):
```scss
.hamburger-menu { anchor-name: --hamburger-menu; }
.dialog-hamburger {
  position-anchor: --hamburger-menu;
  position-area: bottom span-right;
  margin-block-start: toRem(22);
  position-try-fallbacks: flip-block;
}
```

**Почему был заменён на absolute (история):** в desktop-ветке стоит `inset: auto` — он нужен, чтобы
**сбросить mobile-базу `inset: 0`** (базовый `.dialog-hamburger { inset: 0 }`, ~строка 490). Но `inset` —
shorthand для `top/right/bottom/left`, и он **перезаписывает вычисленные от якоря инсеты** → диалог
отваливается от якоря, остаётся в static-position, падает наверх и накрывает кнопку
(верх 167px vs низ кнопки 208px). Поэтому оставлен `position:absolute; top: calc(100% + 22px)`.

**Как обойти (перейти на anchor):**
1. Убрать в desktop-ветке `inset: auto` (shorthand) — он убивает `position-area`. Вместо него явные
   свойства + отступ через `margin-block-start` (не `top`, т.к. `top` задаёт якорь):
   ```scss
   @media (min-width:$mobile) {
     position: absolute;
     position-anchor: --hamburger-menu;
     position-area: bottom span-right;
     inset-inline: auto 0;      // горизонталь своей базой; вертикаль — от якоря
     margin-block-start: toRem(22);
   }
   ```
2. **Якорь на desktop-инстансе.** `.hamburger-menu` у desktop и mobile — разные элементы; общий
   `anchor-name: --hamburger-menu` (строка 447-449) матчит mobile. Перенести на desktop-кнопку:
   `.hamburger_desktop .hamburger-menu { anchor-name: --hamburger-menu; }`.
3. **База `inset:0`** (строка 490) оставляем для mobile — нормально, desktop-ветка его не перебивает
   shorthand'ом, а якорь сам задаёт top.

**Подводные камни:**
- **Поддержка:** Anchor — только совр. Chrome/Edge/Safari/FF (Chrome 125+, Safari 17.4+). На старых
  `position-area` игнорируется → нужен **fallback absolute** (текущий). Anchor — прогрессивное улучшение.
- **`@supports (anchor-name: --x)`** → anchor, иначе → absolute fallback.

## Калькулятор (обсуждение 10.09)

Найдено по референсу (пункт «КАЛЬКУЛЯТОР» в меню). Варианты:

- **A. «Вес → цена»** — ❌ **отклонён**: минимальный заказ от **1 кг**, а цена уже за 1 кг → это
  тривиальное умножение, отдельный калькулятор не нужен.
- **B. «Под задачу» / заготовки** — ✔ **выбран первый сценарий** (варенье, закрутки, сок):
  пользователь задаёт цель («N банок варенья»), калькулятор считает **сколько кг** ягод/продукта
  нужно → стоимость → **«В корзину»**. Справочник норм (выход варенья и т.п.) — минимальный словарь
  (позже можно в Strapi).
- **C. Агро-калькуляторы** (семена ↔ площадь посадки, дозировка удобрений, кол-во рассады) —
  📌 **в план, на будущее**: сейчас нет товаров категорий «семена/удобрения/рассада». Когда
  появятся — нужны справочники (норма высева, схема посадки, дозировка) в Strapi.
- **D. Доставка** (вес/зона → стоимость) — ✔ **встраиваем в КОРЗИНУ** (не отдельный калькулятор).
  Тарифы — **простыми правилами** на первом этапе (значения — на усмотрение разработчика, позже
  возможен перенос в Strapi).

**Взаимодействие (решение 10.09):**
- Реализуем через **`<dialog>`** (не Popover API): калькулятор — модальная форма с вводом, нужен
  focus-trap, backdrop, Escape, блокировка фона — это нативный `dialog` (`showModal`).
  Popover API — для лёгких необязательных панелей (как `MoreMenuPopover`), без модальности.
- **Desktop — страница**, **ниже desktop — модалка** (тот же маршрут).
- **SEO-связка модалки со страницей** — по паттерну `DiscountProduct.vue`:
  реальный `<NuxtLink>` на страницу (индексируется) + микроразметка `itemscope/itemprop`
  (`schema.org/Product`), а скрытый SEO-контент — через класс **`.visually-hidden`**
  (`base/_utils.scss`: `position:absolute; 1×1px; clip-path: inset(100%); overflow:hidden`).
  Страница — с `useSeoMeta` + `application/ld+json` (как остальные страницы проекта).
  Модалка и страница делят один кэш-ключ данных (паттерн `ShowModalProduct`:
  `product-${locale}-${slug}`).
- Открытие — из пункта **«Калькулятор»** в табе «Меню».

**Локализация:** обязательно ru/be — тексты через `frontend/app/locales/*.ts`, справочники (если в
Strapi) — локализуемые поля.

**Предварительный набор рецептов (нормы условные, 10.09):**
| Рецепт | Ед. ввода | Условная норма |
|---|---|---|
| Сок | л | ~1,5 кг → 1 л |
| Компот | л | ~0,3 кг → 1 л |
| Морс | л | ~0,4 кг → 1 л |
| Варенье | л/банка | ~1 кг ягод → 1 л |
| Джем | кг | ~1 кг → 0,8 кг |
| Пюре | кг | ~1,2 кг → 1 кг |

> Нормы — **произвольные/предварительные**, легко правятся. Набор рецептов — уточняется.

**Открытые вопросы:**
- Финальный набор рецептов (оставить/убрать/добавить) и точные нормы.

**Тех. ограничение корзины (`stores/useCartStore.ts`, 10.09):**
- `CartItem = { product, quantity: number }`, но `quantity` — **целое**: `addToCart` делает `+1`,
  `updateQuantity` — `Math.max(1, quantity)`, `totalPrice = price × quantity`.
- Товар priced **за 1 кг**, 1 единица = 1 кг; **минимальный заказ от 1 кг**.
- ⇒ Калькулятор должен считать в **целых кг** (`Math.ceil(нужно_кг)`) и добавлять `quantity = N`.
  Дробный вес корзина сейчас не поддерживает (потребовал бы доработки стора).

**Сценарии и модель (уточнено 10.09):**
- Делаем **несколько рецептов сразу** единым **списком рецептов** (каждый — коэффициенты/единицы), а не
  по одному. Архитектура одинаковая, нормы условные.
- **Односоставные** рецепты (сок, компот, варенье, пюре) — сырьё одно: пользователь выбирает товар →
  количество → кг. Реализуем все.
- **Многосоставные** (консервация/соленья/лечо) — требуют **выбора нескольких** продуктов, сложнее UI →
  **второй этап**.
- Ингредиенты вне каталога (сахар, соль, уксус, банки) — **приписка «докупите отдельно»** (или
  добавление, если появятся в магазине).
- **Результат → «В корзину»**: подтверждено, целыми кг (`Math.ceil`). ВНИМАНИЕ: `addToCart` сейчас
  **не принимает `quantity`** (`quantity` внутри = 1 / `+1`) → требуется **небольшое расширение стора**:
  опциональный параметр `quantity` (`addToCart(product, slug, sub, quantity?)`; для существующей позиции
  `quantity += N`, для новой — `quantity: N`).

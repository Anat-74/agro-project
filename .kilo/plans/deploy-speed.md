# Ускорение деплоя на хостинге (план)

Статус: не начато. Записано 14.11 вместе с планом перехода на pnpm.

## Как это работает (факты)

- `nuxt build` **собирает всё приложение целиком** (клиент + серверный бандл Nitro). Инкрементальной
  сборки «по одной странице» в production-режиме нет — это ограничение бандлера, а не хостинга.
  Инкремент есть только в `nuxt dev`.
- **Изменения контента в Strapi сборку не требуют вообще** — страницы SSR, данные тянутся в рантайме
  (у товаров TTL 60 c). Пересборка нужна только при изменении КОДА.
- Текущий деплой: Plesk → `git pull` → install зависимостей → `nuxt build` (основное время, 3–5 мин) → перезапуск.

## Что даёт ускорение (по убыванию эффекта)

1. **Собирать не на Plesk, а локально/в CI и выкладывать артефакт.**
   `nuxt build` на быстрой машине → загрузить `.output/` + `package.json` (только prod-зависимости) →
   перезапуск. На Plesk остаётся `pnpm i --prod` (или вообще без него, если `.output` самодостаточен
   для Nitro node-server) + restart. Экономия — минуты, и сборка перестаёт зависеть от CPU хостинга.
2. **pnpm + постоянный store на сервере** (`pnpm i --frozen-lockfile`): установка ~1–2 мин → 20–40 c.
3. **Собирать только изменившееся приложение**: фронт (`frontend/`) и бэк (`backend/`) — отдельные
   приложения. Меняется только Strapi — Nuxt не пересобираем вовсе (и наоборот).
4. **Кэш сборки**: `node_modules/.cache`, `.nuxt` и кэш Vite между запусками на Plesk (если хостинг
   позволяет хранить каталоги между деплоями). Даёт 10–30%, но требует аккуратности: устаревший
   кэш иногда ломает сборку.
5. **Меньше работы в сборке**: не включать sourcemaps в проде, не гонять typecheck в build,
   минимизировать список `prerender`/routeRules (пререндер дорогих маршрутов — только там, где нужно).
6. **GitHub Actions + cache**: `pnpm/action-setup`, кэш `~/.pnpm-store`, шаг build, затем деплой
   артефакта. Даёт стабильное время и лог сборки (сейчас причина падения Plesk-build не видна).

## Про «пересобирать только одну страницу»

Так не получится в prod: страницы — части одного бандла. Но можно **не пересобирать вообще**, если
изменение — контент (Strapi). А если правка только в одном файле — сборка всё равно полная, зато
вариант (1) делает её предсказуемо быстрой вне хостинга.

## Порядок

1. pnpm (см. `npm-to-pnpm.md`) — установка и lockfile.
2. Замерить фактическое время этапов деплоя (pull / install / build / restart).
3. Реализовать (1) или (6) — выкладку артефакта вместо сборки на Plesk.
4. Проверить: деплой < 2 мин, прод работает, откат — предыдущий `.output`.
